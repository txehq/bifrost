## Overview

The `bfl` provider is Black Forest Labs' own API for FLUX images and FLUX 3 video. BFL serves images only as tasks: a submit returns an id and a `polling_url`, and the result is polled.

<Note>
BFL images are served only on the image task routes. The sync routes `POST /v1/images/generations` and `/v1/images/edits` return `UnsupportedOperationError` (HTTP 400, `error.code` `unsupported_operation`) for `bfl` without calling BFL.
</Note>

### Supported Operations

| Operation | Route | Status |
|-----------|-------|--------|
| Image generation task | `POST /v1/images/generations/tasks` | ✅ |
| Image edit task | `POST /v1/images/edits/tasks` | ✅ |
| Image task query | `GET /v1/images/tasks/{task_id}` | ✅ |
| Image task cancel | `POST /v1/images/tasks/{task_id}/cancel` | 400 `provider_cancel_unsupported`: BFL has no cancel API |
| Sync image generation and edit | `/v1/images/generations`, `/v1/images/edits` | ❌ |
| Video create, query, download (FLUX 3 Video) | `POST /v1/videos`, `GET /v1/videos/{video_id}`, `GET /v1/videos/{video_id}/content` | ✅ |
| Video cancel | `POST /v1/videos/{video_id}/cancel` | 400 `provider_cancel_unsupported`: BFL has no cancel API |
| Video delete, list, edit, remix | | ❌ |
| Chat, Embeddings, Speech, Files, Batch, List Models, everything else | | ❌ |

## Setup & Configuration

`network_config.base_url` defaults to BFL's global endpoint, `https://api.bfl.ai`. Set it to a regional endpoint such as `https://api.eu.bfl.ai` or `https://api.us.bfl.ai` to keep requests in one region.

<Tabs>
<Tab title="API">

```bash
curl -X POST http://localhost:8080/api/providers \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "bfl",
    "keys": [
      {
        "name": "bfl-key-1",
        "value": "env.BFL_API_KEY",
        "models": ["flux-2-pro", "flux-kontext-pro"],
        "weight": 1.0
      }
    ],
    "network_config": {
      "base_url": "https://api.eu.bfl.ai"
    }
  }'
```

## Authentication

The API key is sent in the `x-key` header. No `Authorization` header is sent, and an `extra_headers` entry named `x-key` does not replace the key.

## Errors

BFL's errors are FastAPI bodies. `detail` is either a string or a list of validation errors. Bifrost keeps the status code (a 429 stays 429), puts the text in `error.message`, and for a validation list writes each entry as `field: msg`. The first entry's field goes in `error.param` and its `type` in `error.code`. `extra_fields.error_type` follows the status:

| Status | Meaning at BFL | `error_type` |
|--------|----------------|--------------|
| 401, 403 | Missing or invalid key | `provider_auth_failed` |
| 402 | Insufficient credits | `provider_billing` |
| 422 | Invalid parameters | `caller_invalid_request` |
| 429 | Rate limit, or too many active tasks | `provider_rate_limited` |
| 500 | BFL failure | `provider_server_error` |
| 503 | BFL unavailable | `provider_overloaded` |

BFL reports moderation as a task status (`Request Moderated`, `Content Moderated`), not as an HTTP error. The image task operation maps it.

## Image tasks

Each route is one call to BFL; Bifrost stores no task. A create is `POST /v1/{model}` (the model is the endpoint name, such as `flux-pro-1.1` or `flux-kontext-pro`) and returns the task object with `status` `queued`. A query is one `GET /v1/get_result`.

```bash
curl -X POST http://localhost:8080/v1/images/generations/tasks \
  -H "Content-Type: application/json" \
  -d '{
    "model": "bfl/flux-pro-1.1",
    "prompt": "A red fox in fresh snow",
    "size": "1024x768",
    "callback_url": "https://hooks.example.com/tasks/123",
    "webhook_secret": "my-signing-secret",
    "safety_tolerance": 2
  }'

curl http://localhost:8080/v1/images/tasks/<id from the create>
```

### Request fields

The unified fields are converted per model, from BFL's OpenAPI. A field the model has no counterpart for is refused with 400 `caller_unsupported_parameter`, `error.param` naming it, before any call to BFL. `seed` is dropped where a model has none. Fields outside the unified set (`safety_tolerance`, `prompt_upsampling`, `webhook_secret`, `image_prompt`, ...) are sent to BFL unchanged.

| Unified field | BFL field | Notes |
|---------------|-----------|-------|
| `size` (`WIDTHxHEIGHT`) | `width`, `height` | Models with width and height; refused on Kontext |
| `aspect_ratio` | `aspect_ratio` | FLUX 3 Image and Kontext |
| `resolution` (`1K`, `2K`, `4K`) | `resolution` (`1k`, `2k`, `4k`) | FLUX 3 Image |
| `output_format` | `output_format` | Refused on `flux-3-image` |
| `num_inference_steps` | `steps` | `flux-dev`, `flux-2-flex`, fill, FLUX 3 Image Klein |
| `input_images`, edit `images` | `images` (FLUX 3), `input_image`, `input_image_2`, ... (FLUX.2, Kontext), `image` (fill) | Bytes are sent as base64, URLs unchanged, a data URL as its base64 payload |
| edit `mask` | `mask` | `flux-pro-1.0-fill` only |
| `callback_url` | `webhook_url` | Refused on `flux-3-image` and `flux-3-image-klein`, which have no webhook |
| `n` | | One image per task: any value other than 1 is refused |
| `response_format` | | Only `url` |
| `client_reference_id`, `expires_after_seconds`, `output_storage_uri` | | BFL has no external task id, deadline or storage target: always refused |

A model outside this table receives only the prompt and the extra fields; any unified field that would need converting is refused.

### The task object

| Field | From BFL |
|-------|----------|
| `id` | `{BFL id}%7C{model}[%7C{polling host}]:bfl`: the BFL id, the model and a regional polling host, joined by a URL-encoded vertical bar. It carries the model (for the link lifetime) and a regional polling host. The host is honoured only when it is BFL's own (`api.bfl.ai`, `api.<region>.bfl.ai`) |
| `status`, `provider_status` | BFL's nine statuses: `Pending` is `queued`; `Reasoning`, `Generating` are `in_progress`; `Ready` is `completed`; `Request Moderated`, `Content Moderated`, `No Card Generated`, `Error`, `Task not found` are `failed`. `provider_status` keeps BFL's string |
| `error` | A failed task's BFL status as `error.code` |
| `content_filter` | Both Moderated states: `filtered_count` 1, `reasons` from BFL's `details["Moderation Reasons"]` |
| `data` | `result.sample` as `{type: "url", url, content_type}` |
| `completed_at`, `expires_at` | `result.end_time`; `expires_at` is one hour later for FLUX 3 models and ten minutes later otherwise. Both are absent when BFL reports no end time |
| `usage.vendor_cost` | BFL's `cost`, `unit` `credit`: the submit's cost on the create, the settled cost on a query |
| `usage.input_megapixels`, `usage.output_megapixels` | The submit's `input_mp`, `output_mp` (the query does not report them) |

## FLUX 3 Video

The model is `flux-3-video`; any other model on `POST /v1/videos` is refused with 400. A create is exactly one `POST /v1/flux-3-video`; a dropped connection is returned as the error and the create is never sent again. A query is one `GET /v1/get_result`, and the task id has the image task id's form, with the model `flux-3-video`. Only that id is a video id: a bare BFL id, or an image task's id, is refused with 400 on the query and the download, before the key is sent.

| Unified field | BFL field | Notes |
|---------------|-----------|-------|
| `prompt` | `prompt` | |
| `seconds` | `duration` | A whole number, or `auto` |
| `aspect_ratio` | `aspect_ratio` | |
| `resolution` | `resolution` | `720p` is `hd`, `1080p` `fhd`, `1440p` `qhd`, `2160p` `uhd`; BFL's own values pass unchanged; other tiers are refused |
| `audio` | `generate_audio` | |
| `input_reference` | `keyframes`, with `mode` `i2v` | Not together with a `keyframes` extra field |
| `video_uri` | `start_video`, with `mode` `v2v` | |
| (none) | `mode` | `t2v` unless the inputs imply `i2v` or `v2v`; a `mode` extra field (such as `draft_enhance`) wins |
| `size`, `output_format`, `last_frame`, `reference_images` | | Refused: BFL has no counterpart |
| `callback_url`, `client_reference_id`, `expires_after_seconds`, `output_storage_uri` | | Refused: the endpoint has no webhook, external id, deadline or storage target, so a lost create response cannot be recovered |

Extra fields (`draft`, `draft_cache`, `keyframes`, `safety_tolerance`, ...) are sent unchanged. `duration` and `generate_audio` are BFL's names for `seconds` and `audio`, which BFL bills by: as extra fields they are refused with 400 `caller_unsupported_parameter` unless the request sends the unified field with the same value, and the body is always written from the unified field. `seed` and `negative_prompt` have no BFL counterpart and are not sent.

The query maps BFL's statuses as for image tasks. A completed task's `videos[]` holds the sample link (`type` `url`, `content_type` `video/mp4`), `expires_at` is two hours after BFL's `end_time`, and `usage.vendor_cost` is BFL's cost in credits. `GET /v1/videos/{video_id}/content` fetches the sample link through the media fetcher, which reaches public addresses only, through the provider's proxy, and sends no key. The file is forwarded as it arrives, never held whole.
