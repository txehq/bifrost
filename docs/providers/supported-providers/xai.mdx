## Overview

xAI is an **OpenAI-compatible provider** powering the Grok family of models. Bifrost delegates to the OpenAI implementation with standard parameter filtering. Key features:
- **Full OpenAI compatibility** - Chat, text completion, and responses
- **Vision support** - Image URLs and base64 encoding for multimodal models
- **Streaming support** - Server-Sent Events with delta-based updates
- **Reasoning support** - Extended thinking for Grok reasoning models
- **Tool calling** - Complete function definition and execution
- **Parameter filtering** - Removes unsupported OpenAI-specific fields

### Supported Operations

| Operation | Non-Streaming | Streaming | Endpoint |
|-----------|---------------|-----------|----------|
| Chat Completions | ✅ | ✅ | `/v1/chat/completions` |
| Responses API | ✅ | ✅ | `/v1/responses` |
| Text Completions | ✅ | ✅ | `/v1/completions` |
| Image Generation | ✅ | - | `/v1/images/generations` |
| Image Edit | ✅ | - | `/v1/images/edits` |
| Context Compaction | ✅ | - | `/v1/responses/compact` |
| List Models | ✅ | - | `/v1/models` |
| Embeddings | ❌ | ❌ | - |
| Video Generation | ✅ | - | `/v1/videos/generations`, `/v1/videos/{request_id}` |
| Speech (TTS) | ✅ | ❌ | `/v1/tts` |
| Transcriptions (STT) | ✅ | ❌ | `/v1/stt` |
| Files | ✅ | - | `/v1/files` |
| Batch | ✅ | - | `/v1/batches` |

<Note>
**Unsupported Operations** (❌): Embeddings return `UnsupportedOperationError`, as do streamed speech and streamed transcription.
</Note>

# 1. Chat Completions

## Request Parameters

xAI supports all standard OpenAI chat completion parameters. For full parameter reference and behavior, see [OpenAI Chat Completions](/providers/supported-providers/openai#1-chat-completions).

### Filtered Parameters

Refused, never removed: `prompt_cache_key`, `prompt_cache_retention` and `prompt_cache_options` set what is cached and for how long, so they change the price. When the model's capability record does not list one, the request returns `400 caller_unsupported_parameter` naming the field and nothing is sent to xAI.

Removed for xAI compatibility:
- `verbosity` - Anthropic-specific
- `store` - Not supported
- `service_tier` - Not supported

### Usage

`usage.server_side_tool_usage_details` carries the per-tool call counts xAI reports for tools it ran itself (`web_search_calls`, `x_search_calls`, `code_interpreter_calls`, `file_search_calls`, `mcp_calls`, `document_search_calls`), on chat completions as on Responses. The final streamed frame carries the same counts as the non-streamed answer. It is absent when xAI reports none.

### Reasoning Support

xAI's `grok-3-mini` model supports extended reasoning via the standard `reasoning_effort` field:

```json
{
  "model": "xai/grok-3-mini",
  "messages": [...],
  "reasoning_effort": "high"
}
```

<Warning>
**Model-Specific Feature**: The `reasoning_effort` parameter is only supported by `grok-3-mini`. Other Grok-3 and Grok-4 models will return an error if this parameter is specified.
</Warning>

Bifrost converts from the internal `Reasoning` structure to xAI's `reasoning_effort` string format.

### Vision Support

xAI vision models support both image URLs and base64-encoded images:

```json
{
  "model": "xai/grok-2-vision-1212",
  "messages": [{
    "role": "user",
    "content": [
      {"type": "text", "text": "What is in this image?"},
      {"type": "image_url", "image_url": {"url": "https://..."}}
    ]
  }]
}
```

**Supported Image Formats:**
- ✅ Image URLs
- ✅ Base64-encoded images
- ✅ Multiple images per message

xAI supports all standard OpenAI message types, tools, responses, and streaming formats. For details on message handling, tool conversion, responses, and streaming, refer to [OpenAI Chat Completions](/providers/supported-providers/openai#1-chat-completions).

# 2. Responses API

xAI's Responses API is forwarded directly to `/v1/responses`:

```
ResponsesRequest → /v1/responses → ResponsesResponse
```

Same parameter support and message handling as Chat Completions. Full streaming support available.

Fields outside the unified structure, such as xAI's `max_turns`, are merged into the request sent to `/v1/responses` unchanged, streamed or not, with or without `x-bf-passthrough-extra-params`.

# 4. Image Generation and Edit

xAI's image endpoints take JSON. Generation goes to `/v1/images/generations` in the OpenAI request shape; edit goes to `/v1/images/edits` in xAI's own shape (xAI does not take a multipart edit).

**Request Conversion**

- **Model & Prompt**: `bifrostReq.Model` → `model`, the prompt → `prompt`
- **Generation parameters**: `n`, `response_format`, `aspect_ratio`, `resolution`, `quality` and `user`, in the OpenAI request shape. Any other field (`size`, `style`, `output_compression`, `output_format`, `background`, `moderation`, `partial_images`, `input_images`, ...) is refused with 400 `caller_unsupported_parameter` before any upstream call. `size` is not mapped: xAI sizes an image by `aspect_ratio` and `resolution`, and a pixel size does not correspond to one documented pair. `seed` and `negative_prompt` are exempt and not sent
- **Edit parameters**: `n`, `response_format`, `aspect_ratio`, `resolution`, `quality` and `user`. Any other price-affecting field (`size`, `mask`, `background`, `output_format`, ...) is refused with 400 `caller_unsupported_parameter`
- **Edit source images**: one image goes in `image`, several (up to five) in `images`, each as `{"url": ..., "type": "image_url"}`. A URL or data URI is sent unchanged; image bytes (multipart upload or JSON `image` bytes) are sent as a data URI
- **`quality`**: sent on `grok-imagine-image-2.0`, the only model xAI documents as taking it. On any other model it is refused with 400 `caller_unsupported_parameter`, `error.param: quality`, before any upstream call
- **`resolution`**: the unified tier (`1K`, `1.5K`, `2K`) is sent in xAI's spelling (`1k`, `1.5k`, `2k`); another tier is refused with `caller_unsupported_parameter`
- **`deferred`**: refused with 400 `caller_unsupported_parameter`, `error.param: deferred`. The image routes return the image from one upstream call; a deferred request would need polling

**Response Conversion**

- `data` holds the delivered images. An image xAI marks `respect_moderation: false` is blocked: it takes no slot in `data` and is counted in `content_filter.filtered_count` (xAI gives no reason code, so `reasons` is empty). When every image is blocked, `data` is `[]`. When an image was blocked, `extra_fields.raw_response` is withheld even if raw-response send-back is on, because xAI's body still carries the blocked image
- `usage.output_images` is the number of images in `data`
- `usage.vendor_cost` is `{"amount": <cost_in_usd_ticks>, "unit": "usd_ticks"}` when xAI reports `cost_in_usd_ticks`; `usage.cost` is derived from the same value
- With raw-request-body mode on, the caller's body is sent to xAI as written, and the typed-field checks above are skipped: they apply to the body Bifrost builds, not to a body it forwards
- With large-payload optimisation on, an edit whose upload crosses the request threshold is refused with 400: xAI's edit takes JSON with the image inlined, so the streamed multipart body cannot be forwarded. A large generation request is streamed through as before
- With a large-response threshold configured, a response over it is streamed to the caller as xAI sent it, without the `content_filter` and `vendor_cost` normalisation above, which needs the whole body in memory
- Errors are parsed in xAI's `{"code", "error"}` shape (or the OpenAI envelope). A content-block code keeps the vendor's status and sets `extra_fields.error_type: caller_content_filtered`

**Streaming**: Image generation and edit streaming are not supported by xAI.

# 6. Context Compaction

xAI supports context compaction via its OpenAI-compatible `/v1/responses/compact` endpoint. Bifrost forwards the request to `https://api.x.ai/v1/responses/compact`.

Request and response format is identical to [OpenAI Context Compaction](/providers/supported-providers/openai#14-context-compaction). The response `output` contains the original user messages plus a final item with `type: "response.compaction"` and `encrypted_content`. Pass this output as `input` to future xAI Responses API calls.

**Endpoint**: `POST /v1/responses/compact`

## Batch API

xAI batches run on the unified batch routes. Each line is an OpenAI-shape chat request, and the batch's results come back per line in OpenAI shape.

**Create** (`POST /v1/batches`) takes inline `requests` whose `url` is `/v1/chat/completions` (other request types are refused with `caller_unsupported_parameter`), or an `input_file_id` from `POST /v1/files`. Inline lines reach xAI as two calls: the batch is created by name, then every line is added with `batch_request_id` set to its `custom_id`. Each line's body goes through the same conversion as the sync chat route. A batch runs one model, the request's `model` (required for inline lines): a line may omit `model` or name the same model, with or without the `xai/` prefix or through a key alias, and a line naming another model is refused with `400`. xAI has no metadata field, so the batch's `metadata` is written into its name as a query string (`tokun_batch_id=batch_123`) and read back on retrieve and list; `display_name` is used as the name when there is no metadata.

```bash
curl -X POST http://localhost:8080/v1/batches \
  -H "Content-Type: application/json" \
  -d '{
    "model": "xai/grok-4.3",
    "endpoint": "/v1/chat/completions",
    "completion_window": "24h",
    "metadata": {"tokun_batch_id": "batch_123"},
    "requests": [
      {"custom_id": "line-1", "method": "POST", "url": "/v1/chat/completions",
       "body": {"model": "grok-4.3", "messages": [{"role": "user", "content": "Hello"}]}}
    ]
  }'
```

**Retrieve and list** (`GET /v1/batches/{id}?provider=xai`, `GET /v1/batches?provider=xai`) map xAI's `state` counters to `request_counts` (`total`, `pending`, `completed`/`succeeded`, `failed`, `canceled`). xAI reports no batch status, so it is derived: `cancelling` or `cancelled` after a cancel, `completed` once nothing is pending, `expired` past `expires_at` with requests pending, `validating` while a file batch has no requests yet, and `in_progress` otherwise.

**Results** (`GET /v1/batches/{id}/results?provider=xai&limit=100&after=<next_cursor>`) page through xAI's results, also while the batch runs. Each line carries `custom_id`, `status` (`succeeded`, `failed`, `expired`, `cancelled`), and either `response.body` (an OpenAI chat completion whose `usage` is the sync route's, with `usage.vendor_cost: {amount, unit: "usd_ticks"}` from xAI's `cost_in_usd_ticks`) or the vendor's `error`. `has_more` and `next_cursor` page the results.

**Cancel** (`POST /v1/batches/{id}/cancel?provider=xai`) calls xAI's `:cancel`. A refusal keeps xAI's status and body and carries `extra_fields.error_type: provider_cancel_unsupported`.

**Governance.** A file batch runs the models named in the uploaded rows, not the request's `model`, as on OpenAI and Azure. Under a virtual key that restricts xAI models, a file batch is refused unless the key allows every xAI model; inline batches are checked line by line against the allowlist. Extra fields on an inline line (anything the chat request does not model) are forwarded only when passthrough extra params is enabled, as on the sync chat route. A line the sync chat route would refuse is refused the same way, before any call to xAI, with `error.param` naming the line's field (for example `requests[1].body.service_tier` for a service tier outside the model's catalog list).

# 7. Video Generation

xAI video generation is an asynchronous task: `POST /v1/videos` creates it, `GET /v1/videos/{id}` queries it, and `GET /v1/videos/{id}/content` downloads the finished video.

**Request Parameters**

| Bifrost field | xAI field | Notes |
|---------------|-----------|-------|
| `prompt` | `prompt` | |
| `seconds` | `duration` | A whole number of seconds. A fractional value returns `400 caller_unsupported_parameter` |
| `aspect_ratio` | `aspect_ratio` | Sent as given |
| `resolution` | `resolution` | Sent as given (`480p`, `720p`, `1080p`) |
| `size` | `aspect_ratio` + `resolution` | Only a `WIDTHxHEIGHT` that is exactly one of xAI's ratios at one of its tiers (`1280x720` is `16:9` at `720p`). Any other size returns `400 caller_unsupported_parameter` |
| `input_reference` | `image.url` | First frame: a URL or a data URL, sent as given |
| `last_frame` | `last_frame.url` | A URL or a data URL, sent as given |
| `reference_images` | `reference_images[].url` | URLs or data URLs, sent as given |
| `output_storage_uri` | `output.upload_url` | A presigned URL xAI uploads the video to |

Fields outside this table (`keyframes`, `reference_audios`, `storage_options`, `user`, `generate_audio`, and any other xAI field) are merged into the request unchanged. `callback_url`, `client_reference_id`, `expires_after_seconds`, `audio` and `output_format` cannot reach xAI and return `400 caller_unsupported_parameter` without an upstream call.

<Note>
A video create is written to xAI **exactly once**, also when the connection fails. xAI cannot find a task again without its request id, so a repeated create would be a second billed task. A create that gets no response is not retried even when `network_config.max_retries` is above zero, and no fallback runs. It returns `502 provider_connection_failed`; whether xAI started the task is unknown. An xAI error response (4xx, 5xx) is an answer, so it follows the ordinary retry rules.
</Note>

**Task object**

| xAI | Bifrost |
|-----|---------|
| `status` `pending`, `done`, `failed`, `expired` | `status` `in_progress`, `completed`, `failed`, `expired`; the xAI value is kept in `provider_status` |
| `video.url` | `videos[0]` with `type: "url"`, a public link |
| `video.duration` | `seconds` and `usage.output_seconds` |
| `usage.output_tokens` | `usage.output_tokens` |
| `usage.cost_in_usd_ticks` | `usage.vendor_cost` with `unit: "usd_ticks"` (1 USD = 10,000,000,000 ticks), and `usage.cost` in USD |
| `video.respect_moderation: false` | `status: "failed"` with `content_filter: {filtered_count: 1, reasons: ["respect_moderation"]}`; `provider_status` stays `done` |
| `error.code`, `error.message` | `error.code`, `error.message` |

xAI states no lifetime for `video.url`, so `expires_at` is not set. `POST /v1/videos/{id}/cancel` returns `400 provider_cancel_unsupported`.

# 8. Speech (TTS)

`POST /v1/audio/speech` calls xAI's `POST /v1/tts`.

| Bifrost field | xAI field | Notes |
|---------------|-----------|-------|
| `input` | `text` | |
| `voice` | `voice_id` | One voice; a multi-speaker voice list returns `400 caller_unsupported_parameter` |
| `response_format` | `output_format.codec` | `mp3`, `wav`, `pcm`, `mulaw`, `alaw`; any other value returns `400 caller_unsupported_parameter` |
| `sample_rate`, `bit_rate` (extra fields) | `output_format.sample_rate`, `output_format.bit_rate` | Whole numbers |
| `language_code` | `language` | xAI requires it; `auto` is sent when it is absent |
| `speed` | `speed` | Sent as given |
| `with_timestamps` | `with_timestamps` | See below |

Other extra fields (`text_normalization`, `replace`, and any other xAI field) are merged unchanged. `instructions` and the other unified speech fields xAI has no field for return `400 caller_unsupported_parameter` without an upstream call.

The response is the audio bytes with xAI's `Content-Type`. With `with_timestamps: true` xAI answers a JSON envelope: Bifrost decodes its base64 audio and returns the bytes, reports its `duration` as `usage.audio_seconds` (whole seconds, in the `x-bifrost-usage` header), and puts the envelope without the audio in `extra_fields.raw_response`. Without `with_timestamps` xAI reports no duration, so `audio_seconds` is absent.

# 9. Transcription (STT)

`POST /v1/audio/transcriptions` calls xAI's `POST /v1/stt` as a multipart form. `model` and `language` are written first, then every extra form field unchanged (`keyterm` once per value, `diarize`, `multichannel`, `format`, `audio_format`, `sample_rate` and the rest), and `file` last, because xAI may ignore a field that follows the file. A `url` field in place of `file` is sent to xAI as given; Bifrost does not download it.

| xAI | Bifrost |
|-----|---------|
| `text`, `language` | `text`, `language` |
| `duration` | `duration` and `usage: {type: "duration", seconds}` |
| `words[].text`, `start`, `end`, `speaker` | `words[].word`, `start`, `end`, `speaker` |
| `channels`, `words[].confidence` | In `extra_fields.raw_response` only |

`response_format`, `timestamp_granularities` and the other unified transcription fields xAI has no field for return `400 caller_unsupported_parameter` without an upstream call.

## Unsupported Features

| Feature | Reason |
|---------|--------|
| Embedding | Not offered by xAI API |
| Streamed speech, streamed transcription | xAI streams these over WebSocket only |
| Video cancel, delete, list | xAI has no API for them; cancel returns `400 provider_cancel_unsupported` |
| Large-payload passthrough for video, speech and transcription | Each request is converted to xAI's own fields, so it cannot be streamed through unparsed; returns `400` |
| Batch delete | Not offered by xAI API (batches are kept until they expire) |
