## 🍴 Fork changes (txehq/bifrost)

- chore: v2.4.0-sync.6 is a prerelease on top of v2.4.0-sync.5 (TXE-6518). It is the unified structure of the Bifrost–Tokun contract's base part: the request, usage and filter fields every vendor then fills. No provider fills or converts them yet; that is each vendor's own work. v2.3.5 stays the stable release and `latest`
- feat (BF3, structure): unified video create fields `aspect_ratio`, `resolution`, `last_frame` (a URL or data URL, the counterpart of `input_reference`) and `reference_images` (URLs or data URLs), and an image generation and edit field `resolution` (tiers such as `1K`, `2K`, `4K`). They parse from `/v1/videos` JSON, `/v1/images/generations` JSON and `/v1/images/edits` JSON and multipart into the typed parameters (`VideoGenerationParameters`, `ImageGenerationParameters`, `ImageEditParameters`)
- fork: compatibility of BF3. Before this release these names reached providers only as extra params, and `byteplus`, `minimax`, `runway`, `replicate` and every provider that forwards its extra params read them there. The handlers therefore also keep each one in extra params under the same name (`schemas.UnifiedVideoGenerationFields`, `schemas.UnifiedImageFields`, kept out of the known-field tables by a test), so every provider receives exactly what it did before; a provider that converts the typed field deletes the extra. `reference_images` in any shape other than an array of strings (Runway's `[{"uri", "tag"}]`) leaves the typed list empty instead of failing the request, and still reaches Runway as an extra param. The OpenAI-shaped image generation body (`openai`, `azure`, `xai` and the other OpenAI-compatible providers) does not carry the typed `resolution`, so its wire body is unchanged
- feat (BF5): a multipart image edit with passthrough on writes every extra param as a form field (strings verbatim, other values as JSON, keys sorted, before the file parts), as the JSON routes merge them into the body. Before, the OpenAI-shaped multipart writer shared by `openai` and `azure` dropped them all. `/v1/images/edits` turns passthrough on for every request (upstream #3572, as `/v1/images/generations` does), so on that route a multipart edit to `openai` or `azure` now forwards its extra fields with or without `x-bf-passthrough-extra-params`, the way a JSON image request to those providers already did. An extra param named like a field the writer already sends (`size`, `n`, ...) is not written twice; the typed value is sent. Cost: an edit with no extra params allocates exactly as before (85 allocs/op); three string extras take 131, string and object extras 136
- feat (BF6): new usage fields for the quantities the vendor reports, all `omitempty` and nil unless a provider fills them from the vendor's own report (never a count Bifrost made, a request parameter or a default). Image `usage`: `output_images`, `input_images`, `output_megapixels`, `input_megapixels`, `output_tokens_details.reasoning_tokens`, `vendor_cost`. The task object's `usage` (`VideoUsage`): `output_tokens`, `output_seconds`, `input_seconds`, `input_images`, `compute_seconds`, `vendor_cost`. Speech `usage`, including the SSE `speech.audio.done` event: `billed_characters`, `vendor_cost`. The existing `usage.cost`, `input_chars`, `NumInputImages` and `NImages` keep their meaning
- feat (BF6): `vendor_cost` is `{amount, unit}`, the money or credits the vendor reported in its own unit: `usd`, `usd_ticks` (xAI), `credit` (BFL; ElevenLabs character-cost) or `unit` (Kling). `amount` is always written, so a reported zero charge reads as 0
- feat (BF10, structure): image responses carry `content_filter{filtered_count, reasons[]}`, the type video responses already use, for images a vendor blocked while answering 200. A blocked image takes no slot in `data`, and an image response's `data` is always an array, `[]` when every image was blocked, never `null`
- docs: the OpenAPI spec documents the new request fields, the image `content_filter`, the image, video and speech usage fields and the `VendorCost` schema; the video generation response gains its `usage`
- test: offline unit tests in `core/schemas` (request fields, tolerant `reference_images`, JSON round trips with omission when empty, `DeepCopy`, `content_filter` and `data: []`), `transports/bifrost-http/handlers` (the unified routes' JSON and multipart parsing, the fields kept as extra params, the known-field guard) and `core/providers/openai` (the multipart body sent upstream with and without the header, the unchanged image generation body). Provider-harness folder 289 pins BF5 against OpenAI: with and without the header, OpenAI rejects a probe form field by name, so the field reached it
- note: module versions. This fork publishes no core, framework or plugin module versions: their module paths stay `github.com/capsohq/bifrost/...`, their version files and the transport's requires are unchanged, and the workspace builds them from source
- preserved: everything v2.4.0-sync.5, v2.4.0-sync.4, v2.4.0-sync.3, v2.4.0-sync.2, v2.4.0-sync.1, v2.3.5 and earlier releases listed under Fork changes
