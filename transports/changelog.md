## ✨ Upstream

- feat: **MiniMax provider** (`minimax/<model>`). Chat Completions go to MiniMax's OpenAI-compatible `/v1/chat/completions` with `reasoning_split` set, so thinking comes back in `reasoning_content` instead of `<think>` tags; `reasoning_effort: none` becomes `thinking: disabled` (dropped on M3.1, which always thinks), and the effort ladder adds `max`. A non-zero `base_resp.status_code` on a 200 is an error mapped to an HTTP status (upstream d20cb6ace #8622, 64cd3a2d2 #8636, 4039d1fdc #8651)

- fix: the native `/v1/audio/transcriptions` route reads repeated `timestamp_granularities[]` fields, as the `/openai` route already did; before, they fell into extra params as one string (upstream 64cd3a2d2)

## 🍴 Fork changes (txehq/bifrost)

- chore: v2.4.0-sync.4 is a prerelease on top of v2.4.0-sync.3, the fourth batch toward upstream transports/v2.4.0 (TXE-5917). It merges upstream dev 668a660e5..4039d1fdc, the six MiniMax commits, and stops before the BytePlus ModelArk change eab4cf7f2; v2.3.5 stays the stable release and `latest`
- fork: this fork already had its own MiniMax provider. Upstream's `MiniMaxProvider` replaces it: chat moves to upstream's converter (reasoning split, `base_resp` errors) and to the streaming client for streams, which the fork's provider did not use, and image generation moves from an OpenAI-shaped request to MiniMax's native one
- fork: MiniMax text completions are kept. Upstream reports them as unsupported; here `/v1/completions` still goes to the Anthropic-compatible `/text/v1/messages` on the base URL's origin, with `anthropic_beta` extra params forwarded as the `anthropic-beta` header, and the streamed variant now runs on the provider's streaming client
- fork: one provider constant. `schemas.MiniMax` (`"minimax"`) is canonical; the fork's `schemas.Minimax` stays as a deprecated alias of it, and `minimax` appears once in `StandardProviders` and in `SupportedBaseProviders`, so a custom provider can still use `minimax` as its base
- fork: the UI keeps upstream's MiniMax entries in place of the fork's duplicates, and the custom-provider operation list for a `minimax` base gains speech, transcription, image and video operations
- fork: the CI workflows (`pr-tests`, `release-pipeline`, `run-core-tests`) keep the fork's versions. Upstream's `MINIMAX_API_KEY` secrets and `api.minimax.io` egress for the live provider jobs are not taken, so no CI job calls MiniMax
- fork: a settled MiniMax video reports its size as `WxH`, built from the task's resolution tier and ratio (`480P` at `9:16` is `480x853`), instead of the tier label. Video pricing reads the short edge of a `WxH` size, so a `480P` label would have missed the 480p rate; with no ratio the size captured from the request is kept
- fork: a MiniMax speech or transcription stream ends cleanly on its final event (`status` 2, `finish: true`) or a terminal `base_resp` error even when MiniMax keeps the connection open afterwards. The stream marks itself parked, so cleanup abandons the connection instead of draining it; before, a parked or heartbeating upstream held the stream channel open indefinitely. A stream read to EOF marks its body exhausted, so cleanup skips the drain
- fork: when MiniMax's final transcription event (`finish: true`) carries text, it is sent as one more `transcript.text.delta` before `transcript.text.done`, so the deltas add up to the full transcript. The streaming accumulator builds the logged transcript from deltas only, so before this the last segment was dropped from logs
- fork: `BifrostVideoGenerationResponse.BackfillParams` fills `seconds` from the request only when the provider reported none, so a duration the provider normalized survives the core request path. MiniMax clamps an H3-Max request for 2s to 5s; the create response said 2s before and says 5s now. Other providers that leave `seconds` empty are backfilled as before
- fork: a custom provider with `base_provider_type: minimax` enforces its `allowed_requests` on every MiniMax operation (list models, text, chat, Responses, image, video create/retrieve/download/delete, speech, transcription and their streams) before any conversion or upstream call. The provider ignored `allowed_requests` before, which mattered once video, speech and transcription became billable operations here
- fork: MiniMax video downloads fetch the task's signed URL through the SSRF-hardened media fetcher (`providerUtils.FetchMediaURL`): public addresses only, checked at dial time and on every redirect, the provider's proxy honoured, a 256 MiB cap and a 5-minute bound, and errors that name the URL without its signed query. Upstream fetched it with the provider client, whose dialer admits loopback, so a compromised upstream could make Bifrost read an internal address. `FetchAndEncodeURL` keeps its 25 MiB and 20s limits. Both now read a body of known length into one exact-size buffer instead of growing it, so an inline fetch allocates less (120 to 111 allocs/op at 4 KiB, 174 to 149 at 1 MiB)
- fork: the video accounting sweeper settles jobs of a custom provider whose base provider settles video (`base_provider_type: minimax`, `openai`, ...), resolving the base from the provider config while the job keeps the custom name for routing and accounting. Before, those jobs were recorded under the custom name, matched no entry in the settler's list and were never priced, so a video could be downloaded while governance never received its cost
- fork: a downloaded MiniMax video is always served with a `video/*` type: the upstream's type is kept only when it is a well-formed `video/<subtype>`, and anything else (`text/html`, `image/svg+xml`, none) becomes `video/mp4`. `/v1/videos/{id}/content` serves the bytes on the gateway's own origin, so an HTML type from a compromised upstream would have rendered there
- fork: a custom provider built on minimax reports its own name (`GetProviderKey`), as OpenAI-based custom providers do, so its video IDs carry the custom suffix and governance records their owner in the same scope a later retrieve, download or delete checks. Before, IDs were suffixed `:minimax` while requests named the custom provider, so a virtual key that learned another's task ID could reach that video through the shared credential
- fork: the fork's earlier Go names `minimax.MinimaxProvider` and `minimax.NewMinimaxProvider` (original signature) stay as deprecated aliases of upstream's `MiniMaxProvider` and `NewMiniMaxProvider`, as `schemas.Minimax` does for `schemas.MiniMax`
- fork: MiniMax image, video and speech inputs that cannot succeed (no prompt, a malformed size or seconds, an unsupported speech format, a missing voice) are 400s that never reach MiniMax, not 500s a client would retry
- fork: upstream's `transports/bifrost-http/handlers/inference_transcription_test.go` is `inference_test.go` here: the fork's rules allow no underscore before `_test.go` and name a new test file after its source file (`inference.go`)
- test: provider-harness folder 286 pins the MiniMax video lifecycle (create, poll to completion with a `WxH` size, download, delete). H3 bills per output second, so every row is `[PREVIEW]` and runs only with `INCLUDE_PREVIEW=1`
- test: offline httptest tests for MiniMax text completions (endpoint, headers, origin resolution, Anthropic error mapping, streaming) and provider-harness folder 285 for `/v1/completions` on MiniMax, non-streamed and streamed
- test: benchmarks for the MiniMax chat conversion, MiniMax chat and text round trips, and native transcription form parsing. OpenAI, Groq and DeepSeek conversions keep 67, 67 and 2/17 allocs/op; a transcription form without granularities keeps 78. MiniMax chat costs 142 allocs/op where the fork's provider took 105 (reasoning split, `base_resp` check); MiniMax text completions keep 90

Upstream's core and framework changelog entries are folded in above
